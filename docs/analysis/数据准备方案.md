>
> 原则：**先让回测能跑起来（单品种/单年），再逐步扩大范围。**

### 核心问题

```
策略配置:   回测 ag 2020-01 ~ 2025-12
                ↓
         HistoricalBarFeed 打开一个 IBarStore → 一个 .db 文件
                ↓
         但数据分散在 6 个 bars_2020.db ~ bars_2025.db 中
                ↓
         结果：无法直接跑跨年回测
```

### 为什么会有 6 个文件

当初并行导入时用了 6 个 `ToolBox import` 进程同时跑，每个写一个文件。这是正确的导入策略（6 进程并行 vs 单进程串行，快了 5-6 倍）。但导入完成后没有执行 Merge 步骤。

## 解决方案

### 方案 A：合并为单一 SQLite（推荐，当前阶段用）

```
bars_2020.db ─┐
bars_2021.db ─┤
bars_2022.db ─┼──→ bars_history.db（完整版，9.5 GB）
bars_2023.db ─┤
bars_2024.db ─┤
bars_2025.db ─┘
```

**实现方式：** SQLite ATTACH + INSERT INTO 合并

```sql
-- 在 sqlite3 中执行
ATTACH 'data/bars_2021.db' AS y2021;
INSERT INTO bars_history.bars_1min SELECT * FROM y2021.bars_1min;
INSERT INTO bars_history.bars_day   SELECT * FROM y2021.bars_day;
DETACH y2021;
-- 重复 2022 ~ 2025
```

或者用 `ToolBox` 写一个 `merge` 命令：
```bash
ToolBox merge --source data/bars_202*.db --target data/bars_history.db
```

**优点：**
- 简单直接，`HistoricalBarFeed` 不需要任何改动
- 一个文件 = 一个 `IBarStore` 实例 = 一次查询
- SQLite 单表 6000 万行没问题（已验证）

**缺点：**
- 最终文件 ~10 GB，传输/备份慢
- SQLite 是行存，跨品种查询效率不如列存

**预计工时：** 写 `merge` 命令 1-2h + 合并运行 ~30min

---

### 方案 B：多 DB 查询层（中期，Phase 2b 后期）

不改 `HistoricalBarFeed`，而是在 `IBarStore` 实现层做多库路由：

```csharp
public class MultiFileBarStore : IBarStore
{
    private readonly Dictionary<int, SqliteBarStore> _stores; // year → store
    
    public async Task<IReadOnlyList<Bar>> QueryBarsAsync(
        string instrumentId, DateTime start, DateTime end, string table, CT ct)
    {
        // 按年份拆分查询范围，分别查对应的 DB
        var results = new List<Bar>();
        for (int y = start.Year; y <= end.Year; y++)
        {
            if (_stores.TryGetValue(y, out var store))
            {
                var yStart = y == start.Year ? start : new DateTime(y, 1, 1);
                var yEnd   = y == end.Year   ? end   : new DateTime(y, 12, 31);
                var bars = await store.QueryBarsAsync(instrumentId, yStart, yEnd, table, ct);
                results.AddRange(bars);
            }
        }
        return results;
    }
}
```

**优点：** 不需要合并文件，保持现有数据布局

**缺点：** 跨年边界查 2 次，但开销可忽略

**预计工时：** 2-3h

---

### 方案 C：迁移到 DuckDB（长期，Phase 3）

`DuckDBStore` 已经实现了完整的 `IBarStore` 接口。迁移步骤：
1. SQLite → CSV 导出（ToolBox export）
2. DuckDB 导入（列存，压缩率 3-5x，跨品种分析快 10-100x）
3. 切换到 `DuckDBStore`

**触发条件：** 当回测需要同时查询 50+ 品种的 Bar 时，SQLite 行存会成为瓶颈。

## 其他数据问题

### 问题 2：合约代码映射（策略 → DB 查询）

**现状：**
```
策略配置:  instruments: ["ag", "rb", "cu"]     ← Future.Code
DB 中存储:  instrument_id: "ag2608", "ag2607"  ← 具体合约
```

`HistoricalBarFeed.QueryBarsAsync("ag", ...)` → **查不到数据**。

**解决（已部分实现）：**

`ContractCodeGenerator.Generate(future)` 可以将 `ag` → `["ag2606", "ag2607", ..., "ag2705"]`（12 个活跃合约）。回测需要为每个合约分别查 DB。

需要在 `HistoricalBarFeed` 或策略初始化层做这个展开。这是 Phase 2a 端到端验证就要解决的问题。

### 问题 3：Tick CSV 目录位置不对

`src/TradingStudio/TickData/` 下有 542 个 CSV 文件。应该移到 `data/ticks/`。

```bash
mv src/TradingStudio/TickData/* data/ticks/
# 然后更新 LiveDataCollector 中的输出路径配置
```

### 问题 4：bars_history.db 大小异常

6/14 是 5.2 GB（2020 全年），6/16 变成 3.4 GB。可能原因：
- 执行了 VACUUM（SQLite 回收空间）
- 或者部分数据被误删

**建议：** 合并前先验证 `bars_history.db` 的 `SELECT COUNT(*), MIN(bar_time), MAX(bar_time) FROM bars_1min`。

### 问题 5：Zero-Volume Bar

5-7% 的 1min Bar 的 Volume = 0。这些是无成交的分钟。回测时策略是否需要过滤它们？

**建议：** 先不做引擎级过滤。策略自己判断 `if (bar.Volume == 0) return`。后续可以加一个 `HistoricalBarFeed` 的可选参数 `skipZeroVolume: true`。

### 问题 6：数据与 dist/ 分离

`data/` 目录用于持久化数据（数据库、CSV），`dist/` 用于构建输出。当前这已经做到了——`data/` 在 `.gitignore` 中。但要确保 `release/` 目录也有独立的 `data/` 或 `AppData/` 路径。
